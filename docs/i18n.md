# Internationalisation

Audience: contributors who want to add a new language or polish an existing one.

## Supported locales and source of truth

The authoritative list of supported locales lives in the backend at [`server/src/lib/locales.js`](../server/src/lib/locales.js). The frontend mirrors the same list inside the `SUPPORTED` set of [`public/js/core/i18n.js`](../public/js/core/i18n.js). Adding a language means updating both files, along with the storage layer described in [Step 3](#step-3-card-translations).

The fallback language is English. When a key is missing from the user's locale, the English entry is used. When a card has no translation for the user's locale, `getCardText` picks English, and if that too is missing it falls back to the first available language.

## UI strings

Two stores exist for user-visible text. Both use flat JSON files with dotted keys such as `login.title` or `admin.users.create.submit`.

- [`public/locales/en.json`](../public/locales/en.json) holds English, the fallback language.
- [`public/locales/fr.json`](../public/locales/fr.json) holds French.

Placeholders use double curly braces. For example, `"home.title": "Welcome, {{a}} and {{b}}!"` is called with `t('home.title', { a, b })` and the helper interpolates the values. For plurals, declare the CLDR variants on the same root key: at minimum `key.one` and `key.other`, and optionally `zero`, `two`, `few` and `many`. Call `tn(key, count, params)` and the helper picks the right variant through `Intl.PluralRules`.

Static HTML carries a fallback value inside the element plus a `data-i18n="key"` attribute. The fallback must match the English locale string exactly, because it is the text shown before JavaScript boots. A quick sanity check runs from the repo root:

```bash
node -e "const fs=require('fs'),path=require('path'); const en=JSON.parse(fs.readFileSync('public/locales/en.json','utf8')); function walk(d){for(const n of fs.readdirSync(d)){const f=path.join(d,n),s=fs.statSync(f); if(s.isDirectory()&&n!=='vendor')walk(f); else if(n.endsWith('.html')){const h=fs.readFileSync(f,'utf8'),re=/<([a-zA-Z][a-zA-Z0-9-]*)\b[^>]*?data-i18n=\"([^\"]+)\"[^>]*?>([^<]*)<\/\1>/g; let m; while((m=re.exec(h))){const t=m[3].trim(); if(!t) continue; if(en[m[2]]!==t) console.log(f,'key='+m[2],'HTML=\"'+t+'\" EN=\"'+en[m[2]]+'\"');}}}} walk('public');"
```

## Adding a new language

Adding a language is a three-step process. Each step is independent, and you can ship an incomplete language (for example, UI strings without card translations) as long as the English fallback is in place.

### Step 1. User-interface strings

1. Copy [`public/locales/en.json`](../public/locales/en.json) to `public/locales/<code>.json`. The `<code>` must be the ISO 639-1 two-letter identifier (for example `de` for German or `es` for Spanish).
2. Translate every value. The keys themselves must stay identical because they are referenced from the code. The file must contain the same set of keys as `en.json`.
3. Edit [`public/js/core/i18n.js`](../public/js/core/i18n.js) and add the new code to the `SUPPORTED` set:

   ```js
   const SUPPORTED = new Set(['en', 'fr', '<code>']);
   ```

4. Add a `settings.language.<code>` entry in every locale file so the language name shows up in the selector. Use the native name of the language, for example `"settings.language.de": "Deutsch"`.
5. Retest every screen after the change, including the admin panel. See the [Testing translations](#testing-translations) section below.

### Step 2. Web app manifest

The server negotiates the manifest based on the request's `Accept-Language` header. To ship a translated manifest for the new language:

1. Copy [`public/manifest.en.webmanifest`](../public/manifest.en.webmanifest) to `public/manifest.<code>.webmanifest`.
2. Translate the `name`, `short_name` and `description` fields.
3. Extend the negotiation inside [`server/src/routes/manifest.js`](../server/src/routes/manifest.js) so the new code is matched against `Accept-Language`.

A limitation of the PWA spec is worth knowing: once the app is installed on a device, the displayed name is fixed to the manifest served at install time. Changing the in-app language later does not rename the icon on the home screen. This is a browser-side constraint, not a CoupleCards one.

### Step 3. Card translations

Card text is stored separately from the structural fields (id, pile, foil, sort order). The database table `card_translations` holds one row per card and per locale. To ship cards in the new language:

1. Create `data/cards.<code>.json`. The file structure mirrors the existing English and French seed files exactly:

   ```json
   {
     "version": 1,
     "cards": [
       { "id": "home-001", "pile": "home", "title": "...", "description": "..." },
       { "id": "home-036", "pile": "home", "title": "...", "description": "...", "foil": true }
     ]
   }
   ```

   The `id`, `pile` and `foil` fields must match what the other locale files declare for the same card. The seed and deck-sync helpers refuse to merge files whose structural fields disagree. Only `title` and `description` carry language-specific text.

2. Widen the `CHECK` constraint on `card_translations.locale` so the new code is accepted. Since the production schema lives in [`server/migrations/001_init.sql`](../server/migrations/001_init.sql), ship a new numbered migration rather than editing the initial file:

   ```sql
   -- server/migrations/002_locale_<code>.sql
   -- SQLite cannot ALTER a CHECK constraint. We rebuild the table in place.
   CREATE TABLE card_translations_new (
     card_id     TEXT NOT NULL REFERENCES cards(id) ON DELETE CASCADE,
     locale      TEXT NOT NULL CHECK (locale IN ('fr','en','<code>')),
     title       TEXT NOT NULL,
     description TEXT NOT NULL,
     PRIMARY KEY (card_id, locale)
   );
   INSERT INTO card_translations_new SELECT * FROM card_translations;
   DROP TABLE card_translations;
   ALTER TABLE card_translations_new RENAME TO card_translations;
   CREATE INDEX idx_card_translations_locale ON card_translations(locale);
   ```

3. Extend [`server/src/lib/locales.js`](../server/src/lib/locales.js) by adding the new code to `SUPPORTED_LOCALES`. This single change propagates to the seeder, the deck-sync helpers and the admin routes.

4. On a fresh install, the first boot imports every `cards.*.json` automatically. On an existing instance, trigger the same import through the admin panel: Cards tab then **Sync from the files**. Pick **Add and update** to preserve the existing deck, or **Full mirror** to replace it entirely.

5. The admin card editor picks up the new language automatically because it reads the same `SUPPORTED_LOCALES` list; new entries get one text block per locale in the card dialog.

## Testing translations

- Switch the language from inside the app (Settings, then Language) and walk through every screen, including the admin panel.
- Cards on the draw, history and banned-cards screens must update immediately without a reload. If a card has no translation for the chosen language, the English fallback should show up.
- Use the browser's developer tools to simulate a different `Accept-Language` on an uncached load, and confirm that the correct manifest is served.
- Clear `localStorage.couplecards:locale` before reloading to test automatic detection from the browser language.
- On the login and forced-change-password pages, the logo and labels should appear in the detected language before any click.

## Font coverage

The bundled fonts are Inter for the sans-serif stack and Literata for the serif stack. Both ship the Latin extended, Cyrillic, Greek and Vietnamese subsets, so any translation that uses one of these scripts works out of the box.

For scripts outside this range (CJK, Arabic, Hebrew, Thai or the Indic family), you need to ship an extra font. Add a new `@font-face` rule in [`public/css/fonts.css`](../public/css/fonts.css) with the matching WOFF2 file in `public/fonts/`, then adjust the `--font` and `--font-display` custom properties in [`public/css/themes.css`](../public/css/themes.css) if you want the new face to take precedence for that script.

## Consistency tips

- Keep placeholders such as `{{a}}` identical in every language.
- Avoid colloquialisms that do not localise well. Keep the voice warm but neutral.
- Spacing and punctuation around placeholders matter. French uses a thin space before `:` and `!`, whereas English does not.
- Submit translations in the same pull request as the code that references the new keys; this avoids intermediate commits where a language is missing strings.
